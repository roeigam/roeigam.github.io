Traffic Tracker

Solo Project · Computer Vision & Vehicle Tracking

Point it at any traffic video and it tracks every vehicle by a persistent ID across frames, works out the single frame where each one passed closest to the camera, and exports an annotated video, a CSV with every vehicle's closest-approach data, and a snapshot image per vehicle — automatically, no manual review of hours of footage required.

§01 · How it worksdetect → track → score → export

Every frame gets run through YOLOv8 filtered to vehicle classes only (car, motorcycle, bus, truck). ByteTrack then carries each detection's identity across frames, so the same car keeps the same ID from when it enters the frame to when it leaves. For every tracked vehicle, a closeness heuristic runs on every frame it appears in — the single best frame per vehicle gets kept, and everything else is discarded.

§02 · Tuning the trackercustom_bytetrack.yaml

Default tracker settings weren't built for cars accelerating toward a fixed camera — vehicles grow rapidly in frame as they approach, which breaks a tracker's default matching assumptions. Every value below was changed on purpose, not left at the library default.

custom_bytetrack.yamlreal config, comments included
tracker_type: bytetrack

# Raise this to ensure only solid detections start/maintain tracks
track_high_thresh: 0.4

# Raise this to filter out noise that creates "ghost" second IDs
track_low_thresh: 0.2

# Increase this to be "pickier" about starting a brand new ID
new_track_thresh: 0.5

# Keep this high to bridge gaps if a car is momentarily lost
track_buffer: 60

# LOWER this (counter-intuitive, but important!) — 0.8 is very strict;
# lowering it allows more flexibility in matching, especially as cars
# grow rapidly in size as they get closer to the camera.
match_thresh: 0.6

fuse_score: True
§03 · Picking the closest framescoring.py

"Closest to camera" has no depth sensor to fall back on — just a 2D bounding box. The proxy used here is the box's bottom edge (a car lower in frame is standing on ground closer to the camera), with bounding-box area as a tiebreaker for cases where two vehicles land at a similar height in frame.

main.pycloseness_score()
def closeness_score(xyxy):
    """
    Proxy for "closest to camera".
    We prioritize the bottom y (y2): lower in image => likely closer.
    Secondary tie-breaker: bbox area.
    """
    x1, y1, x2, y2 = xyxy
    area = max(0.0, (x2 - x1)) * max(0.0, (y2 - y1))
    return float(y2), float(area)

That score feeds a running "best so far" dict keyed by track ID — every new frame either beats the current best for that vehicle or gets thrown away.

§05 · What's nextnear-term roadmap

The script works, but it's still a script — a few things are already planned to make the repo itself read as engineered, not just the pipeline it runs.

NEXT UP

Repo hygiene

Proper .gitignore, stop tracking generated outputs and model weights directly in git — the model already auto-downloads on first run.

THEN

Package structure

Split the single script into focused modules — scoring, drawing, video I/O, tracker state, and a thin CLI — same logic, organized into testable units.

THEN

Tests & CI

Unit tests for the scoring and per-track selection logic, a smoke test on a trimmed sample video, and a GitHub Actions workflow running lint + tests on every push.

THEN

Docs & polish

A proper README with the architecture and tuning rationale, a license, and real logging instead of print statements.

STRETCH

Speed & direction estimation

Using bottom-center position deltas across frames — ties the project to actual traffic analysis, not just detection.

STRETCH

Interactive demo

A small Streamlit or FastAPI wrapper so results are explorable instead of "run the CLI, open the CSV."
