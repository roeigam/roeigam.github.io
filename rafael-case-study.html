Rafael Case Study

Release Automation & Tooling

On a mission-critical communications program, I owned release engineering end to end for a team of three software integrators — carrying the largest share of prototype hardware — with DevOps, CI/CD automation, and QA all managed through Git and run daily in Linux and Bash. I built the tooling that packaged, versioned, and documented every release, then gated each one through a sanity-check process before it ever reached a lab or office. That work included templated, portable release notes that render anywhere, and a one-click versioning tool that replaced hours of manual work, alongside a stream of smaller scripts that removed everyday friction for the whole team.

A separate desktop tool from this same role is covered in the Ferry Case Study →

§01 · The problembefore this existed

Release notes were written and maintained as Word documents — accurate, but painful to keep that way. Every release meant re-editing a formatted document by hand, and the result only worked well on a machine with Office installed and configured to match. That made it a poor fit for a lab floor: nobody wants to open a laptop and hunt for the right version of Word just to check what changed. It didn't display cleanly on shared lab screens, wasn't easy to pull up on a phone during a walk-through, and every editing pass risked breaking the formatting for the next person. Creating a new release was its own separate manual process — done by hand, one step at a time, with no tooling behind it.

Validation had the same gap: there was no agreed, written definition of what a release had to pass before it was trusted outside our own hands. Whether a build was actually ready for a lab or an office came down to whoever happened to test it that cycle, not a fixed standard.

§03 · Portable release notesHTML template → Linux render → PDF

I moved the release-note format from a Word document to a pre-built HTML template — the layout and tables stay fixed, and only the content that actually changes between releases gets edited. A Linux script then renders that HTML into a PDF automatically. A PDF opens identically on any device with no editing software required, so the same release note could go up on a lab TV, get shared in a group session on a shared computer, or get pulled up on someone's phone mid-conversation — something the old Word-based version never handled.

§05 · One-click versioninga manual sequence → a single command

Creating a new release used to be a fully manual sequence. I built a tool that turns it into an interactive checklist: it walks through what's being included in the release, then on confirmation automatically names and numbers the new version in sequence, packages it, produces an encrypted build alongside the standard one, and generates that version's release note from the same HTML template — all from a single command instead of a manual, multi-step process.

release-tool.shversion, package, encrypt
current_version=$(cat VERSION.txt)
read -p "New version (current: $current_version): " new_version

echo "Packaging release $new_version..."

§06 · Distributioncurl · Basic Auth · artifact repository

Once a release was packaged, it still had to reach an internal artifact repository — by hand, that meant logging in and dragging files through a browser every cycle. I scripted the upload: it prompts for credentials once, then loops through every packaged file and pushes it over HTTP with Basic Auth, checking the response code so a failed upload is never mistaken for a successful one.

upload-artifact.shcredentialed loop upload
read -p "Username: " username
read -s -p "Password: " password; echo
credentials=$(printf "%s:%s" "$username" "$password" | base64)

for file in build/*.tar.gz; do
  echo "Uploading $file..."
  status=$(curl -s -o /dev/null -w "%{http_code}" \
    -H "Authorization: Basic $credentials" \
    -T "$file" "$ARTIFACT_REPO_URL/")

  if [ "$status" -eq 201 ]; then
    echo "Success"
  else
    echo "Upload failed (HTTP $status)"
  fi
done

§07 · Everyday scriptingPython · Bash

Beyond the two larger tools, I wrote a steady stream of smaller Python and Bash scripts aimed at removing day-to-day friction — for myself and for the other integrators on the team. As one of three integrators covering the most prototype hardware on the team, small time sinks repeated across every unit added up fast. One example: checking whether a given process was actually alive on a prototype used to mean checking it manually, one at a time — I wrote a status script that reads the expected process list from a config file and reports every one at once with a clear running/NOT running label, color-coded green or red.

status-check.shprocess status, at a glance
proc_names=$(grep 'command=' "$CONFIG_FILE" | sed -n 's/.*command="\([^"]*\)".*/\1/p' | awk -F'/' '{print $NF}')

for proc in $proc_names; do
  if pgrep -x "$proc" > /dev/null; then
    printf "%-15s ----- \e[32m%s\e[0m\n" "$proc" "running"
  else
    printf "%-15s ----- \e[31m%s\e[0m\n" "$proc" "NOT running"
  fi
done

Provisioning a batch of similar units also meant giving each one a distinct network identity — by hand, that meant editing multiple config files per unit and keeping the numbering consistent across all of them. I scripted it: give the tool a unit ID, and it derives the correct subnet address from that ID and writes it into every config file that needs it, so a unit is fully addressable on the network from a single command instead of a manual per-file edit.

set-unit-id.shderive address from ID, propagate to configs
unit_id=$1

# Derive a subnet address from the numeric unit ID
octet_3=$(( unit_id / 100 ))
octet_4=$(( unit_id % 100 ))
new_addr="10.${octet_3}.${octet_4}"

echo "Assigning unit ID $unit_id → address $new_addr"

# Propagate the new address to every config file that references it
for config_file in /etc/network/interfaces /etc/dhcp/dhcpd.conf; do
  sed -i "s/10\.[0-9]*\.[0-9]*/${new_addr}/g" "$config_file"
done

echo "$unit_id" > /etc/unit/unit-id.conf
echo "Unit $unit_id provisioned at $new_addr"

Port conflicts on shared lab hardware were another recurring headache — two people spinning up services on the same box with no easy way to see what was already taken. I wrote a scanner that checks a port, a single range, or a full default range, and reports only what's actually in use, with the owning process name alongside it.

check-ports.shfind what's already in use
check_port() {
  local port=$1
  local result=$(netstat -paun 2>/dev/null | grep ":$port ")
  if [ -n "$result" ]; then
    local process=$(echo "$result" | awk '{print $NF}')
    echo "Port $port ($process) is in use"
  fi
}

if [ $# -eq 0 ]; then
  for port in $(seq "$PORT_MIN" "$PORT_MAX"); do check_port "$port"; done
elif [ $# -eq 1 ]; then
  check_port "$1"
else
  for port in $(seq "$1" "$2"); do check_port "$port"; done
fi

Hardware validation was another area worth automating rather than doing by eye. One prototype's security module occasionally failed to initialize on boot — usually recoverable with a single reboot, but not always. I wrote a check that detects the module, tries exactly one automatic reboot if it's missing, and then fails loudly and stops retrying if it's still missing afterward, so a real hardware fault gets flagged instead of silently reboot-looping.

check-security-module.shdetect → retry once → flag
module_exists() { [[ -e /dev/tpm0 ]]; }

if module_exists; then
  touch "$OK_FLAG"
  exit 0
fi

if [ ! -e "$OK_FLAG" ]; then
  echo "$(date) module not found, retrying once via reboot" >> "$LOG_FILE"
  touch "$OK_FLAG"
  reboot
fi

echo "$(date) module still missing after reboot — flagging failure" >> "$LOG_FILE"
rm -f "$OK_FLAG"
exit 1

File paths and config field names have been generalized; the logic in all four (process parsing, ID-to-address derivation, port scanning, and single-retry hardware recovery) matches what I built.

§08 · Validation & impactquality bar, day to day

Validation

Every master version I built had to clear a sanity-check spec I wrote together with my team lead — a fixed, agreed set of checks run on our own prototype hardware before anything moved further. I ran that suite myself on every release. A clean pass meant the build moved on to the labs and offices; a failure meant I dug in to find and fix the cause myself. When the root cause sat outside what I owned, I looped in whoever did own that piece and worked the fix through with them rather than guessing — so nothing shipped past us without either passing outright or being properly understood first.

Internal & customer-facing support

Provided ongoing hands-on support to lab colleagues and engineering teams working with these releases day to day, and traveled internationally to support customers directly on-site — deployment, troubleshooting, and training on our products in the field.
